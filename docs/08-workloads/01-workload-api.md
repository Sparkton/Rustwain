# Workload API

**K8s analogue:** Pod, ReplicaSet, Deployment, StatefulSet, DaemonSet, Job, CronJob,
ControllerRevision, PodTemplate.

## Pod (the unit)

```yaml
kind: Pod
metadata: { name: web-1, namespace: shop }
spec:
  isolation: process
  serviceAccount: web
  init:                          # ordered: run-to-completion steps and sidecars
    - name: proxy
      sidecar: true
      image: ghcr.io/acme/proxy@sha256:...
  containers:
    - name: app
      image: ghcr.io/acme/web@sha256:...
      command: ["/app/web"]
      args: ["--port=8080"]
      env: [ { name: MODE, value: prod }, { name: DB_PASS, secret: { name: db, key: password } } ]
      ports: [ { name: http, port: 8080 } ]
      resources: { requests: { cpu: 250m, memory: 256Mi }, limits: { memory: 512Mi } }
      probes: { readiness: { http: { port: http, path: /ready } } }
      security: { runAsUser: 1000, readOnlyRootFilesystem: true }
      volumeMounts: [ { name: cache, path: /cache } ]
  resources: { limits: { cpu: "2" } }           # optional pod-level budget
  volumes: [ { name: cache, scratch: { size: 1Gi } } ]
  restart: { policy: Always }
  terminationGrace: 30s
  placement: { ... }                             # see placement doc
  priority: normal
  dns: { policy: ClusterFirst }
```

Users rarely create Pods directly; controllers do.

## Workload controllers

### Deployment
Stateless replicated pods with rolling updates.

Kubernetes implements Deployment → ReplicaSets (one per template revision) → Pods. The
ReplicaSet layer is mostly an implementation detail that leaks into UX (users see
`web-7d9f8c` ReplicaSets, old ones kept for rollback).

Rustwain `[proposed]`:
- Deployment → **Revision** objects (immutable template snapshots, like
  ControllerRevision) → Pods labelled with revision hash. The Deployment controller
  manages pods directly per revision (no separate ReplicaSet controller).
- Rollback = point Deployment at an earlier Revision.
- `revisionHistoryLimit` default 10.
- Optional standalone `ReplicaSet` kind only via import adapter.

Fields: `replicas`, `selector` (immutable, auto-generated by default from name to prevent
the "overlapping selectors" footgun), `template`, `strategy` (RollingUpdate{maxSurge,
maxUnavailable} | Recreate | Canary – see rollouts doc), `minReadySeconds`,
`progressDeadline`, `paused`.

### StatefulSet
Pods with stable identity: ordinal names (`db-0`, `db-1`), stable DNS
(`db-0.db.shop.svc`), per-replica Claims from templates, ordered/parallel pod management,
partitioned rolling updates.

Improvements `[proposed]`:
- **Fencing-aware replacement**: when a node is unreachable, `db-1` isn't recreated until
  the old instance is fenced (Kubernetes simply never replaces it automatically until the
  pod is force-deleted – correct but painful). We automate the safe path.
- `maxUnavailable` for rolling updates (Kubernetes added as alpha, 1.24+).
- Volume replacement policy for local storage (`Abandon` → new empty claim when node lost).
- Start ordinal (Kubernetes 1.27+ `ordinals.start`) for migrations.
- **Claim resizing via template** – Kubernetes forbids changing `volumeClaimTemplates`
  (KEP-4650 in progress); we allow size increases propagating to existing claims.

### DaemonSet
One pod per matching node. Rolling updates with `maxUnavailable` and `maxSurge`.
Scheduled by the **scheduler** (not the controller assigning nodes directly; Kubernetes
moved to scheduler-based DaemonSet placement in 1.12+) using node-name affinity per pod,
so resources/taints/devices are handled uniformly.

### Job
Run-to-completion pods: `completions`, `parallelism`, `completionMode: Indexed`
(each pod gets an index), `backoffLimit` (+ per-index limits), `activeDeadline`,
`podFailurePolicy` (rules on exit codes / disruption conditions: e.g. don't count
evictions against backoffLimit), `successPolicy` (succeed when index 0 succeeds – for
leader-worker patterns), `suspend`, `ttlAfterFinished`.

Kubernetes accreted these over many releases; we design them in from the start, since
they all live in one controller.

### CronJob
Schedules Jobs: cron syntax with **time zones** (`timeZone: Europe/London`),
`concurrencyPolicy` (Allow | Forbid | Replace), `startingDeadline`, history limits.
Missed-schedule semantics: Kubernetes refuses to start if > 100 missed schedules (a
confusing error). Rustwain: "run at most once for missed windows, then continue" with an
event noting the skip.

## Templates and revisions
- Template changes detected by a **stable hash** of the template's canonical encoding.
  Kubernetes' hashing of pod templates has caused unexpected rollouts on upgrades when
  defaulting changed (new default fields → new hash → every Deployment restarts on
  control-plane upgrade!). Rustwain hashes the **user-specified** template (pre-defaulting)
  to avoid this class of problem `[proposed]`.

## Status
Every workload status has:
- `replicas`, `ready`, `available`, `updated`, `terminating` counts,
- `conditions` with `Ready`, `Progressing`, `Degraded` (standard types),
- `observedGeneration`,
- `currentRevision`, `updateRevision`,
- For failures: aggregated reasons from pods (`3 pods CrashLooping: exit 1 "config missing"`).

`rwctl rollout status` and `rwctl wait --for=Ready` work uniformly.

## Open questions

- Keep a user-visible ReplicaSet kind at all? (Proposed: no, only Revisions.)
- Pod template hashing on user-specified spec: requires storing the original applied
  spec separately from defaults (or defaulting at read).
